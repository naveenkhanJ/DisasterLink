## 0. Conventions

1. **Stereotypes** (lecture, DG §5.4): «boundary» — screens and external services an actor or the system touches; «control» — coordinates a use case between boundaries and entities (the lecture's "at least one control class per use case"; a use case may have several controls); «entity» — domain data. **Persistence is not drawn** (K-1, K-2; reverses decision 8-1): as in the lecture's examples (DG §5.4), controls send messages to entity objects and loading/saving is implicit; every stored entity is saved and loaded by a Spring Data repository listed in §6 (implementation mapping). G-CD-14 (lifelines with no class — UI, Controller, Storage Service, Analytics Service, Database) is answered by CH-10's classes and by removing the `Database` lifelines. **Finder convention (grounded in the lecture's stereotype rules, DG §5.4: entities are "identified by examining the data (information) storage requirements" and controls "coordinate the movement (parameters) between boundary and entity classes"; the lecture's examples, e.g. ManageCourseUI → CourseControl → Course, draw no storage object; FC-20):** controls receive identifiers from boundaries and retrieve the corresponding entity objects; collection queries are operations of the controls; a duplicate replay is drawn as a guard `[duplicate submissionId]`, not as a message. The offline home read is not a message either: SD2 shows `loadHome()` returning `HomeView` with `fromCache = true`; the phone's cache (`HomeCache`, §6) stays implementation-only (FQ3, FD-14). The client stores `OfflineReportStore` (phone) and `OfflineOutbox` (browser) are «entity» classes marked {client} (K-3; the class box shows `{client}` under the name — FD-05): the pending items they hold are what Save Data Offline is about and what the screens show as pending (the case study's "offline data capture, and delayed synchronisation"). **«interface»** types in the entity layer (`Recipient`) and control layer (`MetricCalculator`, `ReportExporter`) are drawn with that keyword; the implementations of the two control-layer interfaces are drawn on the UC4 detail figure (K-8); `Recipient`'s implementers are on the main diagram.
2. **Communication:** actor ↔ boundary; boundary ↔ control; control ↔ control; control ↔ entity. Never boundary ↔ boundary, boundary ↔ entity, entity → entity calls, actor ↔ control. **Displays:** a boundary calls a control and displays the control's **reply**; its `show…` operation is a self-call drawn after the reply; controls never call **screen** boundaries (so the server never depends on the web layer); controls do call **service** boundaries — the notification gateways and `LocationService` — which are the system's interfaces to external actors. **Refusals (RC-02; FD-02, FE-07):** (1) *validation and capacity results of writes* are **replies**, never exceptions: `ShelterOutcome.result.outcome = REJECTED` and `ReportReceipt.result.outcome = REJECTED` (V2C N-08), each with the typed reason `SyncResult.reason : RejectionReason` (OVER_CAPACITY, INVALID_VALUE, VALIDATION_FAILED — V2C-11) and the text in `message`; offline replays get the same replies (a `SyncResult` REJECTED); (2) *interactive refusals of online operations* are **domain exceptions** — `ReasonRequiredException`, `ActiveWarningExistsException`, `InvalidHazardUpdateException` (V2C N-02), `ReportNotSharedException`, `ExportFailedException`, `WarningNotEscalatableException`, `InvalidHazardDetailsException` (P60 N6, N12), `ReportAlreadyDecidedException` (PD5) (table in §6: exception → raised by → display); the sequence diagram draws the exception as the reply named after it, and the boundary shows the matching `show…` display (in the code, the exception handler — implementation-standards §4). No other exceptions are used for refusals (`ShelterCapacityExceededException` is not used). **Confirm-time re-validation (P62 FX-05; R4C-01, R4G-05):** the confirm handler of a previewed write — `WarningDashboardUI.confirmBroadcast`, `EscalationUI.confirmEscalation`, and for UC4 `AnalyticsUI.confirmAdjustedCriteria` or the `enterCriteria` submission that leads to `generateReport` — re-calls the control's validate operation (`validateWarning`, `validateEscalation`, `validateCriteria`) with the stored preview input before it calls the write (`issueWarning`, `escalateWarning`, `generateReport`); when the result is invalid (e.g. the expiry time has passed while the officer stayed on the preview) the screen shows its `showValidationErrors(errors)` and the form keeps its values — drawn in the sequence diagrams as a guard `[invalid]`. This is a validation reply, not a refusal, and adds no exception. The writes do not validate again themselves; called with invalid input they throw `IllegalStateException` (a programming error → 500 → the C1 banner). Push alerts and connectivity changes reach a boundary as **found messages**; a found alert or decision notice is then shown by the boundary's own display (`showAlert`, `showReportDecision` — FD-12). Composite parts are created by the controller and handed to the whole (`Shelter.updateOccupancy(record)`, `Warning.addNotification(n)`). Passing an entity as an argument so that the receiver stores a link (`HazardReport.verify(officer, hazard, at)`, `DisasterReport.shareWith(organization)`) is not an entity → entity call; reads an entity makes of its own parts or of an argument are not drawn (DG §5.7 #12, #14).
3. **Types:** `String`, `int`, `double`, `boolean`, `DateTime` (Java `LocalDateTime`, zone Asia/Colombo), `Date` (`LocalDate`), `List<T>`, `Set<T>`, `Map<K,V>`, `byte[]`. Every ID is `String`. **Screen**-boundary operations return `void`; the service boundaries (the `NotificationGateway` family, `LocationService`) return their results (FD-01). `[0..1]` marks an optional attribute, parameter or result; in the code a `[0..1]` result is `Optional<T>` in Java and `T | undefined` in TypeScript, and a `[0..1]` field **of an entity** may be null but its getter returns `Optional` (FE-06). Record components and `@Embeddable` fields marked `[0..1]` (e.g. `GeoPoint.accuracyMetres`, `HazardDetailsView.activeWarning`, `ShelterOutcome.shelter`, `SyncResult.message`) are nullable and documented (Javadoc `@return … or null`), never `Optional` (V2C-03; implementation-standards §5). A `[0..1]` **parameter** (e.g. `shelterId` of `validateShelterDetails`) is a nullable, documented type in Java, never `Optional`, and `x?: T` in TypeScript (PR15). On the wire a `DateTime` is ISO-8601 with its offset (`2026-05-21T08:15:00+05:30`; PR15). Request and response DTOs therefore use `OffsetDateTime`; the mappers convert to and from `LocalDateTime` in Asia/Colombo (implementation-standards; P62 FX-29, R4G-08).
4. **Creation** is by constructor, drawn as «create»; no class has a `createX()`/`registerX()` operation on itself (CH-19).
5. **Accessors (FE-05):** accessors exist in the code only where a flow or a mapping uses them (no unused members — L03 Dead Code); state changes go through the domain operations, so no public setter bypasses `verify`, `reject`, `updateOccupancy`, `escalate`, `markDelivered`/`markFailed`, …. Value types are Java `record`s and use record accessors (`x()`), with no setters. Accessors are listed here only when a sequence diagram sends them.
6. **Built column:** ✓ = implemented (one of the four use cases, or Escalate Warning / Save Data Offline as part of them); **S** = seed data and persistence only (no flow changes it); **D** = design only (belongs to a use case nobody implements; not coded — L03 Dead Code). The class diagram carries one note: controls and boundaries are drawn for the four use cases, Escalate Warning and Save Data Offline; the other use cases are supported by entities only (round-1 #36). The report states this once.
7. **Design vs code (K-9):** every ✓/S class, attribute and operation exists in the code with exactly this name. Three rules govern classes the diagrams do not show: (1) every sequence-diagram lifeline is a class on the class diagram; (2) an implementation-only class never takes over a responsibility the design gives to a drawn class — a repository query may *select* records by stored values (status, district, period, criteria fields), while *decisions* (validation, capacity, assessability, escalation, sharing) stay in controls and entities; the only exceptions are the helpers named in §6 — `SubmissionRecorder`, `WarningTextValidator` and `CriteriaValidator` — each called by a drawn control whose operation stays on the diagram and delegates to it: a helper evaluates a rule and returns the result, and the calling control makes every workflow decision (PD6; `WarningTextValidator` — L03 Duplicate Code, L04 Extract Class: two controls share its rule; `CriteriaValidator` — L03 Large Class, L04 Extract Class: it keeps `AnalyticsController` clear of the PMD GodClass risk, P62 FX-10, R4C-04); (3) implementation-only classes are listed in §6 so they are built. A «boundary» screen class is implemented as a screen module of that name with one component per screen; its `show…` displays are Thymeleaf templates or fragments (officer screens) or screen components (the app) named after the display (FE-28). An officer-screen boundary is the Spring `@Controller` of that name, with handler methods named after the boundary's inputs; the dictionary's `void` maps to the view name a handler returns (PR15). The code may add implementation-only types the design does not show: DTOs, mappers, Spring configuration, web adapters (including the push mock's poll endpoint over `PushOutbox` and the console's photo-serving endpoint `GET /reports/{reportId}/photo` — P62 FX-29, R4G-34), private helper methods, and the classes in §6 (repositories, `ProcessedSubmission`, the phone's home-screen cache `HomeCache`, `SubmissionRecorder` (R3C-07), `PushOutbox`, `WarningTextValidator`, `CriteriaValidator`, `IdGenerator` with its enum `IdKind`, `MockGatewayFailureRule` (PD6, PR14; `IdKind` P62 FX-12), the utility `GeoDistance` (P62 FX-02), the domain exceptions). **Persistence mapping (implementation):** A8 (Notification → Recipient) is stored as `recipientKind : RecipientKind` + `recipientId`, read from `Recipient.getRecipientKind()` and `getRecipientId()` (V2C-05; `PushOutbox.recipientId` is written the same way). **Recipient resolution (FE-10):** Notifications created in a broadcast keep a transient (not stored) `Recipient` for the gateway call; `resend` resolves the stored `recipientKind` + `recipientId` through a map from `RecipientKind` to a finder (the Citizen, Organization and DistrictOfficer repositories), built in `WarningBroadcaster`'s constructor — no switch; `ReportCriteria` and `ReportResults` are stored as JSON through an `AttributeConverter`. **Optimistic lock (P62 FX-07):** `HazardReport` carries an implementation-only `@Version long version` (§6, under the repositories).
8. **Spelling:** Group_060's names are kept as written (`Organization`, `DisasterReport`, `warningLevel`); a type follows its class (`OrganizationType`); new names use British spelling.
9. **Configurability (round-1 #43; FD-19):** the design is *extended* for a new hazard type or district with one enum literal and its seed data, with no code branches (per-type defaults live in data). This is a small change and rebuild, not run-time configuration; the report states it in these words against the case study's "configured for different hazard types and different districts".
10. **Technical failure (C1, P60):** a server or network failure on an online screen (5xx, timeout, unreachable) is shown by the screen's common error banner, built in the web/app layer and not drawn; nothing is changed; the actor may retry. Scenarios word it "System shows that the service is unavailable and nothing was changed". Officer forms are plain Thymeleaf POSTs: the prototype shows the banner for a 5xx reply, while a lost connection on a form POST shows the browser's own error page — a stated prototype limitation (implementation-standards §4; P62 FX-18). It has no dictionary display and is not a domain exception (§6). Offline-capable writes (the phone's report submission, every UC3 write) follow the offline rules instead (`OfflineReportStore`, `OfflineOutbox`; implementation-standards §4).
11. **Screens and forms (C2, P60):** form screens and pick-lists are screen components, not dictionary displays; a form keeps the values already entered when it is shown again (e.g. after `showValidationErrors`); inputs carry the values the actor entered. **Hazard label (P62 FX-14; R4E-14, R4G-33):** screens label a hazard as its type plus `locationName` ("Flood — Kalu Ganga at Ratnapura"); "Kalu Ganga flood" in the scenarios is narrative. The app's warning DTO (the `getActiveWarnings` reply) carries each warning's hazard type and `locationName` (implementation-standards contract).
12. **Phone draft (C3, P60):** the app screen (`CitizenAppUI`) holds the draft being edited and passes it to `ReportCaptureController.validateDraft` / `submit`.
