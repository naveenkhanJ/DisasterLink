## 2. Traceability to the design

- Every ✓/S class, attribute, operation and literal in `02 Group Design/model-dictionary.md` exists in the code with the same name; sequence-diagram messages map to methods with the same names (rubric: "alignment with use cases, use case scenarios and sequence diagrams"). Implementation-only types (DTOs, mappers, configuration, web adapters) and the classes in MD §6 — the Spring Data repositories, `ProcessedSubmission`, `HomeCache`, `PushOutbox` with its poll endpoint, the shared helper `SubmissionRecorder` (§4, V2C N-07), the validator helpers `WarningTextValidator` and `CriteriaValidator` (§4, PD6), `IdGenerator` with its enum `IdKind` and `MockGatewayFailureRule` (§11, PR14; FX-03, FX-12), the utility `GeoDistance` (§4, FX-02) and the domain exceptions (`ReasonRequiredException`, `ActiveWarningExistsException`, `ReportNotSharedException`, `ExportFailedException`, `InvalidHazardUpdateException`, `WarningNotEscalatableException`, `InvalidHazardDetailsException`, `ReportAlreadyDecidedException`) — are built but not drawn. **Three rules (K-9, MD §0.7):** (1) every sequence-diagram lifeline is a class-diagram class; (2) an implementation-only class never takes over a responsibility the design gives to a drawn class (a repository query may *select* records by stored values — status, district, period, criteria fields — while *decisions* such as validation, capacity, assessability and escalation stay in controls and entities; the only exceptions are the helpers MD §6 lists by name — `SubmissionRecorder`, `WarningTextValidator` and `CriteriaValidator` (PD6): the drawn control operation stays (`validateWarning`, `validateEscalation`, `validateCriteria`) and delegates its rule checks to the helper, which returns its result (a list of errors, a `CriteriaCheck`, a `ProcessedSubmission [0..1]`) and makes no workflow decision — FX-10, R4C-05, R4G-30); (3) every implementation-only class is listed in MD §6. **Design-only (D) members are not coded** (no dead code).
- Every flow of the improved scenario (main, alternate, exception — brief C4) is implemented and tested. Test methods are named after the behaviour (`rejectsOccupancyAboveCapacity`); `@DisplayName` carries the flow ID ("A3 — rejects occupancy above capacity").
- Code implementing a change cites its change ID in the Javadoc ("Implements CH-nn"); `02 Group Design/traceability.md` maps finding → CH-nn → artefacts → code/tests → report section; `01 Analysis/find-refs.py CH-nn --also <repo>` lists every citation.
- Screens follow the improved wireframes exactly (spec: "consistent with the storyboard/ wireframes in the group report").
- **Sequence diagrams before briefs (FE-27):** SD1–SD4 and the Escalate Warning `sd` are drawn and verified before any brief is released; each brief carries its diagrams' message lists in order (sender, receiver, operation, guard), and the code follows that order and those guards. Before the freeze each member checks his code against them: `find-refs.py` for the CH citations, plus a read-through against the message list.
- **Officer-screen boundaries in Java (R3G-18, PR15):** an officer-screen «boundary» (`WarningDashboardUI`, `EscalationUI`, `VerificationConsoleUI`, `AnalyticsUI`, `DonorReportView`, `ShelterManagementUI`) is the Spring `@Controller` of that name in `…<feature>.web`, with one handler method per boundary input, named after it (`selectHazard`, `confirmBroadcast`, …). **Two inputs in one submission (R4G-24, FX-29):** where two boundary inputs arrive in one HTTP submission — `enterWarningDetails(details)` and `requestPreview()` (SC1 step 10) — the form POSTs to the `enterWarningDetails` handler, which binds and stores the details (§4 Preview state) and redirects; the browser then GETs the `requestPreview` handler, which shows the preview (POST → redirect → GET), so each handler is still one boundary input. `enterEscalationDetails(details)` is a single input (PR3) and needs no split. MD §0.3 makes screen-boundary operations `void`; in Java a handler returns the Thymeleaf view name (or a redirect) instead — the report states this `void` → view-name mapping beside the FE-28 mapping below.
- **`show…` displays (FE-28, MD §0.7):** a boundary's `show…` operation is not a Java method. On the officer screens it is a Thymeleaf template or fragment named after the display (`th:fragment="showReasonRequired"`); in the app it is a screen component named after it (`ShowAlert.tsx` for `showAlert`); on the UC3 pages, which the page script draws from `ShelterOutcome` (§10), it is a page-script function with the display's name (`showCapacityExceeded`). The report states this mapping so a marker can find each display.

## 3. Coding standards (L04 §4.1)

- **Naming (Oracle Java conventions):** package root `lk.sliit.se3070.group058.dews` (a reversed domain we can claim — not `lk.gov.dmc`), all lower case, package names are nouns (`notification`, not `notify`); classes and interfaces `UpperCamelCase` nouns; methods `lowerCamelCase` verbs; variables meaningful, never starting with `_` or `$`, one-letter names only for short loop indices; constants `UPPER_SNAKE_CASE`. No Hungarian prefixes, no names describing quality ("BadUtil").
- **Packages by feature, then layer; dependencies point downwards, no cycles:** `…dews.<feature>.web` (Thymeleaf and REST controllers — the boundary adapters) → `…<feature>.service` (controls) → `…<feature>.repository` / `…shared.repository` / `…shared.gateway` → `…<feature>.domain` (the use case's own entities) → `…shared.domain` (shared entities, value types, enums); features = `warning` (UC1 + escalation, Lakmal), `hazardreport` (UC2, Afham), `shelter` (UC3, Weliwitigoda), `analytics` (UC4, Naveenkhan), `shared` (skeleton). Web-layer records sit in `…<feature>.web.dto` and their mappers in `…<feature>.web.mapper`; configuration in `…shared.config`; seed data in `…shared.seed`. The JaCoCo gate is configured per feature package (round-2 CL N-18), so a member's figures include his `<feature>.domain`; `shared.domain` has its own gate (§8).
  - **Package map for the implementation-only classes (R3G-21, PR15):** a repository of a feature entity is in `…<feature>.repository`; the repositories of `shared.domain` entities are in `…shared.repository`; `PushOutbox`, its repository and its poll endpoint are in `…shared.notification`; `SubmissionRecorder`, `IdGenerator` and its enum `IdKind` are in `…shared.service` (`IdGenerator` depends on no feature package — FX-12); the utility `GeoDistance` (`final`, private constructor, `haversineKm(a : GeoPoint, b : GeoPoint) : double`) is in `…shared.domain` (FX-02, R4G-18); `MockGatewayFailureRule` is beside the mock gateways in `…shared.gateway`, and its `dev`-profile toggle endpoint is in `…shared.web` (§11); the photo-serving endpoint `GET /reports/{reportId}/photo` is a web adapter in `hazardreport.web` (§12.3); `WarningTextValidator` is in `warning.service` and `CriteriaValidator` in `analytics.service` (Group_058 decision). Each domain exception is in its feature's `service` package — `warning.service`: `ActiveWarningExistsException`, `InvalidHazardUpdateException`, `WarningNotEscalatableException`; `hazardreport.service`: `ReasonRequiredException`, `InvalidHazardDetailsException`, `ReportAlreadyDecidedException`; `analytics.service`: `ReportNotSharedException`, `ExportFailedException` — and carries `@ResponseStatus` with its 4xx status, so the shared JSON handler in `…shared.web` reads the status from the annotation and imports no feature package (§4 Handlers). **Who writes and who is gated where:** the package → gate → owner table in §8 (R4G-10, R4G-20).
  - **Where entities live (FE-15):** an entity whose rules serve one use case is in that feature's `domain` package, and its rules are written and tested by its owner (the skeleton supplies only its fields and mapping, §11): `hazardreport.domain` — `HazardReport`; `shelter.domain` — `Shelter`, `OccupancyRecord`; `analytics.domain` — `DisasterReport`, `CriteriaTemplate`. Entities used by several use cases stay in `shared.domain` (skeleton): `User`, `Citizen`, `CommunityVolunteer`, `DMCOfficer`, `DMCDutyOfficer`, `DistrictOfficer`, `Recipient`, `Organization`, `Hazard`, `Warning`, `Notification`, `ReliefSupply` and `ResourceDistribution` (seed only), `AuditRecord`, `ClientSyncStatus`, `ProcessedSubmission`, with the enums and the value types that reference no feature entity. **Value types beside the entity they reference (V2C-06):** a value type that references a feature entity lives in that feature's `domain` package — `hazardreport.domain`: `ReportReceipt`, `VerificationOutcome`, `NearbyReport` (FX-02); `shelter.domain`: `ShelterOutcome`, `ShelterView`; `analytics.domain`: `ShareOutcome` (`ReportResults`, `ReportHeader` and `ScopedReport` reference no entity and stay in `shared.domain` — FX-04). `shared.domain` **never imports a feature package**, so dependencies run only from the feature `domain` packages to `shared.domain` and the layering has no cycle. **Device-side types (R3G-02, PR15):** `HomeView` and `SubmissionResult` are built on the phone by `ReportCaptureController` ("Runs on: device") and exist in **TypeScript only** — no Java class (it would be Dead Code, L03 Smell 9), and no server-side home endpoint; the TypeScript type carries the full MD definition. **Operations on shared entities (P132, decision A):** the skeleton writes and tests the cross-use-case derivations and accessors — `Warning.coveredDistricts`, `Warning.statusAt`, `Warning.getNotifications`, `LocalisedText.textIn`, the `Recipient` methods on `Citizen`, `Organization` and `DistrictOfficer` (`getRecipientId`, `getRecipientKind`, `getContactNumber`, `getPreferredLanguage`, `getDeviceToken`, `canReceive`), `ClientSyncStatus.recordSync`, `RiverBasin.districts()` and the utility `GeoDistance` — because skeleton code (the mock gateways, the warning finders) and several use cases depend on them. The owner's tests cover his operations (I14); the report gives its method-level coverage from the JaCoCo HTML report beside his package figures.

## 4. Best practices (L04 §4.2–4.7)

- **Logging:** a logger per class — `private static final Logger LOG = LoggerFactory.getLogger(X.class)` using **SLF4J only** (`org.slf4j.Logger`, `org.slf4j.LoggerFactory`; never `java.util.logging`, never the lab's own `LoggerFactory`); `{}` placeholders; levels ERROR (= JUL SEVERE: a serious failure), WARN (= WARNING: unexpected but survivable), INFO (normal noteworthy events), DEBUG (= FINE: tracing); include the identifier involved; **pass the exception object as the last argument** (`LOG.error("… {}", id, e)`), never only `e.getMessage()` (the stack trace would be lost); levels set per environment in `application.properties` (`logging.level.*`), not in code. **No `System.out`/`System.err`.** **(Spring)** SLF4J is a stack-specific choice, not lecture text: L04's lab mandates `java.util.logging` with `{0}` placeholders, but SLF4J (with Logback) is Spring Boot's default logging stack and L04's own slide example (`logger.warn(...)` with `{}`) is SLF4J style; the report states this justification (R3G-26).
- **Refusals (MD §0.2, RC-02 as revised by FD-02/FE-07) — two kinds:**
  1. **Validation and capacity results of writes are replies, never exceptions (V2C-08):** the `validate…` operations (`validateWarning`, `validateReport`, `validateDraft`, `validateShelterDetails`, `validateCriteria`, `validateEscalation`) return a `ValidationResult`; capacity is judged in `updateOccupancy` (`Shelter.canAccommodate`) and comes back in the `ShelterOutcome` reply — `ShelterOutcome.result.outcome = REJECTED` with its `RejectionReason` (`OVER_CAPACITY`, `INVALID_VALUE`); a rejected report comes back as a `ReportReceipt` with `result.outcome = REJECTED` (V2C N-08); offline replays get the same replies. A reply carrying a typed outcome and its reason is the designed result of these operations, not an error code hiding a failure (L04's "Replace Error Code with Exception" does not apply). A missing rejection reason is not a validation result: it is refusal kind 2 (`ReasonRequiredException`).
  2. **Interactive refusals of online operations are named domain exceptions**, drawn on the sequence diagrams as the reply named after the exception and shown by a `show…` display: `ReasonRequiredException` (`rejectReport` without a reason → `VerificationConsoleUI.showReasonRequired`); `ActiveWarningExistsException` (`issueWarning` for a hazard with an active warning; the exception carries that active `Warning` → `WarningDashboardUI.showActiveWarningExists(warning : Warning)`); `InvalidHazardUpdateException` (`updateHazard` with an invalid update → `WarningDashboardUI.showValidationErrors(errors)`, V2C N-02); `ReportNotSharedException` (`getScopedView` for an organisation the report was not shared with → `DonorReportView.showNotShared()`); `ExportFailedException` (`exportReport` failure, `EXPORT_FAILED` audit recorded → `AnalyticsUI.showExportError`); `WarningNotEscalatableException` (`getEscalationOptions` for an expired warning, or `escalateWarning` for a warning that has expired or is no longer below the chosen level; the exception carries the `Warning` → `EscalationUI.showNotEscalatable(warning)`, P60 N6); `InvalidHazardDetailsException` (`verifyAsNewHazard` with `NewHazardDetails` lacking districts, severity or location name; carries the errors → `VerificationConsoleUI.showValidationErrors(errors)`, P60 N12); `ReportAlreadyDecidedException` (`verifyReport`, `verifyAsNewHazard` or `rejectReport` for a report that is no longer pending, `!report.isPending()`; carries the `HazardReport` → `VerificationConsoleUI.showAlreadyDecided(report)`, PD5; under true concurrency the optimistic-lock rule below maps a lost race to the same exception — FX-07). MD §6's exceptions table is the full list. `ShelterCapacityExceededException` is **not** used.
- **(Spring) Concurrent decisions on one report (FX-07, R4E-07, R4G-25):** `HazardReport` has an implementation-only `@Version long version` field (MD §6 note under the entity mapping; the skeleton maps it). Two duty officers deciding the same report at once can both pass `isPending()`; the second commit then fails with `ObjectOptimisticLockingFailureException`. `ReportVerificationController` maps that failure during `verifyReport`, `verifyAsNewHazard` or `rejectReport` to `ReportAlreadyDecidedException`: it runs the decision in a `TransactionTemplate`, catches the failure **outside** it (the rule under Exceptions below: never catch inside the transaction that failed), re-reads the report for the display and throws `ReportAlreadyDecidedException(report)` → `showAlreadyDecided(report)`. One test proves the mapping (Afham). The exception surfacing at commit is reasoned from Spring and Hibernate behaviour, **not executed**.
- **Handlers (FE-14):** (a) **JSON API** (the app, the UC3 page script, the push poll): one `@RestControllerAdvice(annotations = RestController.class)` in `…shared.web` (skeleton), ordered first (`@Order(Ordered.HIGHEST_PRECEDENCE)`), answers every error as an RFC 9457 `ProblemDetail` with an HTTP status — 400 for a malformed or Bean-Validation-rejected request, 404 for an unknown identifier, the 4xx status declared by the domain exception's `@ResponseStatus` (§3 package map — the advice imports no feature package), 500 for anything unexpected (logged at ERROR with the exception) — and `detail` holds the plain-language message. The TypeScript and JavaScript clients turn a **4xx** `ProblemDetail` reply into a `SyncResult` with `outcome = REJECTED`, `message = detail` and `reason` = `VALIDATION_FAILED` or absent (`reason` is the `RejectionReason` enum, never the text — R4G-31); a **5xx** reply (a server fault, possibly transient) and a network error (no reply) are not rejections — the item stays QUEUED and is sent again on the next replay (V2C-07). Validation and capacity results are not errors: they come back as normal replies carrying `REJECTED` — **HTTP 200** with the typed body (`ReportReceipt`, `ShelterOutcome`; PR15, §11). (b) **Officer screens (Thymeleaf):** each web controller handles its feature's exceptions with its own `@ExceptionHandler` methods, or one `@ControllerAdvice(basePackages = "lk.sliit.se3070.group058.dews.<feature>.web")` per feature, so the handler can re-render the page with its context (`showReasonRequired` re-renders the report detail) and each member owns his own handler — no shared file for four people to merge.
- **(Spring) Preview state between preview and confirm (R3G-13, PR15):** `confirmBroadcast()`, `confirmEscalation()` and `confirmAdjustedCriteria()` take no arguments, so the officer-screen `@Controller` holds the previewed `WarningDetails`, `EscalationDetails` or adjusted `ReportCriteria` in the HTTP session with `@SessionAttributes` (cleared with `SessionStatus.setComplete()` after confirm or cancel), never in hidden form fields. **Session names differ from form names (R4G-09, FX-29):** the form binds to one model attribute (e.g. `warningForm`) and the handler stores the validated input under a different session attribute (e.g. `previewedDetails`); if the two shared a name, Spring would bind the request parameters onto the session object, and a record has no setters, so re-entered values (SC1 A4 12c, E3 11f; Escalate A4 9b, E3 8c; SC4 E4) would be silently dropped and the old preview shown (reasoned from `ModelAttributeMethodProcessor`, **not executed**). The same rule holds on `EscalationUI` and `AnalyticsUI`; the owner picks the names, never equal. **Confirm-time re-validation (FX-05, R4G-05, R4C-01):** the confirm handler (`confirmBroadcast`, `confirmEscalation`; for UC4 `confirmAdjustedCriteria()` or the `enterCriteria` submission that leads to `generateReport`) **re-calls the control's validate operation** (`validateWarning`, `validateEscalation`, `validateCriteria`) with the stored preview input before it calls the write (`issueWarning`, `escalateWarning`, `generateReport`). When the result is invalid — e.g. the expiry time has passed while the officer stayed on the preview — the handler shows the screen's validation display (`showValidationErrors(errors)`, which `WarningDashboardUI`, `EscalationUI` and `AnalyticsUI` all have) and the form keeps its values; nothing is written. This is not a refusal and adds no exception (MD §0.2); the sequence diagrams draw it as a guard `[invalid]`. The write operations do **not** validate again themselves; called with invalid input they throw `IllegalStateException` — a programming error, answered by the 500 path and the common error banner (C1).
- **Technical failures on online screens (C1, MD §0.10, P60):** a server or network failure on an online screen — a 5xx reply, a timeout, or no connection — is not a domain refusal and has no `show…` display: every officer page and every app screen shows it in the screen's **common error banner**, built once in the web/app layer (the Thymeleaf layout fragment; the app's shared screen wrapper) and not drawn on the sequence diagrams. Its text says that the service is unavailable and that nothing was changed (scenarios: "System shows that the service is unavailable and nothing was changed"); the form keeps the values entered (C2) and the actor may retry. **Prototype limitation (FX-18, R4G-14):** the officer forms are plain Thymeleaf POSTs, so the banner is demonstrated for **5xx replies**; a lost connection on a form POST shows the browser's own error page — a stated prototype limitation, here and in the report. (UC3's page script already uses `fetch` and shows the banner for a network error as well, §10.) The server side is the 500 path of the handlers above (logged at ERROR with the exception) and the transaction rollback, so nothing is changed. **Offline-capable writes** — the phone's report submission and every UC3 write through `OfflineSyncController` — do not show the banner for a network error or 5xx: they follow the offline rules (the item is queued, or stays QUEUED on replay — V2C-07).
- **Exceptions:** never swallow; never `catch (Exception e)` where a specific type is meant; combine identical handlers in one multi-catch; custom domain exceptions (e.g. `ReasonRequiredException`) **extend `RuntimeException`**, so that **(Spring)** `@Transactional` rolls back (it rolls back only for unchecked exceptions); never catch-and-continue inside a `@Transactional` service method — **except** where the design records a partial failure, arranged so that no rollback erases the record (FE-12, as revised by FX-27 / R4G-06): (UC4) `generateReport` runs **each calculator in its own read-only `TransactionTemplate`** (`setReadOnly(true)`), so the lazy collections a calculator reads (e.g. `Shelter.getOccupancyRecords()`) load inside a transaction; a failed metric's exception is caught **outside** that template — logged and recorded in `failedMetrics` — so no rollback-only flag spreads to the other metrics; it then saves the report and its audit row together in one `TransactionTemplate` block. `exportReport` is **not** `@Transactional`: it loads the report with what the exporter reads (`provisionalSince`, `sharedWith`, the covered hazards) in a read-only `TransactionTemplate` or through an `@EntityGraph` finder, then runs the exporter, then saves the audit row separately; on failure it saves the `EXPORT_FAILED` audit row (that save commits on its own) and rethrows `ExportFailedException`. **Open-session-in-view is off:** `spring.jpa.open-in-view=false` (§11), so every lazy read happens inside a service transaction and templates read only mapped view records (§5); a `LazyInitializationException` is a bug to fix, not something OSIV hides. (Hibernate lazy-loading behaviour reasoned, **not executed**.) Never rely on `@Transactional(propagation = REQUIRES_NEW)` on a method called from the same bean (self-invocation bypasses Spring's proxy, so the annotation has no effect), and never catch an exception thrown by a Spring Data repository method inside an outer transaction (it has already marked that transaction rollback-only, so the commit fails with `UnexpectedRollbackException`). Lakmal's and Naveenkhan's briefs repeat this. The lecture's three steps, and where each happens: (1) **log** the error with the exception attached and (2) **tell the user** in plain language what went wrong **and what happens next** (never a stack trace) — both in the handler that serves the controller (see Handlers above), named in each web controller's Javadoc (exceptions are not "just thrown upwards": that handler is where they are handled); (3) **roll back** — the transaction boundary of the service method; each use case has at least one test proving a failed operation leaves the repository unchanged. That test is a `@DataJpaTest` against H2 (Boot 4: `spring-boot-starter-data-jpa-test`, in the skeleton POM) that imports the service and switches off the test's own transaction (`@Transactional(propagation = Propagation.NOT_SUPPORTED)` on the test class), so the service's boundary is the one exercised; it runs the failing operation and asserts the stored state afterwards. Because the test has no transaction of its own, whatever it (or its arrange step) writes commits and would leak into later tests that share the cached application context, so each such test class cleans up after every test (V2C-18): `@Sql(scripts = "/cleanup.sql", executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD)` with a script that truncates the tables the test touched (the skeleton supplies the script in its test resources), or deletion through the repositories in an `@AfterEach` method. A Mockito `verify(repository, never()).save(…)` shows only that validation ran before saving and does not count (FE-17). Try-with-resources for every closeable resource.
- **Constants and configuration:** no magic numbers or strings — named `static final` constants or enums; environment-dependent values in `application.properties` (`@ConfigurationProperties`), read with defaults.
- **Supported APIs only:** `java.time` (zone `Asia/Colombo`), no deprecated calls; compile with `-Xlint:all` **without** `-Werror` (FE-18): on Java 21 `-Xlint:all` includes `this-escape`, which fires on ordinary entity and bean constructors; every warning is read and fixed or justified in a comment, never silenced wholesale.
- **Generics:** no raw types; most specific element type; diamond operator.
- **Encapsulation (L03 lab defects):** all fields `private`; getters have no side effects; no public mutable fields; no static mutable state; `equals`/`hashCode` consistent (JPA entities: identifier-based and stable) and `toString` never `null`. **Accessors (FE-05, MD §0.5):** an accessor exists only where a flow, a template or a mapper uses it; state changes only through the domain operations (`verify`, `reject`, `updateOccupancy`, `escalate`, …) — no public setter that bypasses them (an unused setter is Dead Code, L03 Smell 9). JPA needs no setters: map the fields directly (field access) and give each entity a `protected` no-argument constructor.
- **Organisation:** high cohesion, low coupling; create utility or helper classes for reusable logic — a **utility class** is `final`, has a private constructor (throwing `AssertionError`) and only static methods; a **helper class** may be instantiated; neither may grow into a bloated "God Class in disguise".
- **One idempotency and sync-status path (V2C N-07):** the `ProcessedSubmission` check (is this `submissionId` already recorded? — `SubmissionRecorder.check(meta : ClientMeta) : ProcessedSubmission [0..1]`, `Optional` in Java, FX-11; record it when ACCEPTED) and the `ClientSyncStatus` update from `ClientMeta` are implemented **once**, in the skeleton, as the helper class `SubmissionRecorder` (`…shared.service`; implementation-only, listed in MD §6), and called by both `ReportSubmissionController` (UC2) and `ShelterController` (UC3) — neither control re-implements them (Duplicate Code, L03). It decides nothing the design gives to a drawn class (§2 rule 2): validation and capacity stay in the controls and entities.
- **Value objects** are Java `record`s (also DTOs and embeddables) — **never** `@Entity` classes; they use record accessors (`x()`), entities use `getX` getters where a use exists and no bypassing setters (round-2 CL N-19 as amended by FE-05); enums instead of type codes and boolean-flag soups.
- **Input validation** goes through the design's `validate…` operations returning `ValidationResult` (`validateWarning` and `validateEscalation` — incl. the three languages, the SMS length rule and the expiry — both delegating to `WarningTextValidator` (PD6; one rule in one place: L03 Duplicate Code, L04 Extract Class); `validateCriteria`, delegating to `CriteriaValidator` (PD6; L03 Large Class, L04 Extract Class — the PMD GodClass risk of `AnalyticsController`, §6; FX-10, R4C-04); `validateReport(draft, photo)`, which checks the photo too — exactly one, readable, the size and type rules of SC2 step 16 (FX-01); `validateDraft`; `validateShelterDetails`); capacity is judged in `updateOccupancy` and returned in the `ShelterOutcome` reply, and a missing rejection reason is `ReasonRequiredException` (§4 Refusals; V2B-02, V2C-08); Bean Validation (`jakarta.validation`, `@Valid`) on request DTOs checks **only the request's shape** — presence, type, parseability — and **never a rule that has a REJECTED reply or a `show…` display** (no `@Min(0)` on `newTotal`, no `@Size(max = 500)` on `description`: they would turn UC3's `INVALID_VALUE` reply and UC2's REJECTED `ReportReceipt` into 400 errors — R4G-12, FX-29); never rely on database constraints for business rules (D4-06's criticism) (round-2 CL N-25).
- **SMS text separator (FX-09, R4G-22):** an SMS carries a language's message, one separator, then that language's instructions; the separator is one named constant `SMS_TEXT_SEPARATOR = "\n"` (one GSM-7 character, counted as 1), used by both `WarningTextValidator` (the length rule) and `WarningBroadcaster` (the text sent) — the scenario counters agree (SC1 English 116 + 1 + 122 = 239; Escalate 124 + 1 + 134 = 259).
- **No entities on the wire (FE-23):** REST replies never serialise JPA entities (lazy proxies, internal fields): the web layer maps `ReportReceipt.report`, the warnings and reports the app's home screen reads (`getActiveWarnings`, `getReportsByReporter` — `HomeView` itself is built on the phone, §3), `HazardDetailsView` and the like to response records in `…<feature>.web.dto` through mappers in `…<feature>.web.mapper` (implementation-only, MD §0.7); the TypeScript types use the dictionary's names.
- **(Spring) Finders Spring Data cannot derive (FE-09, V2C-09):** **every MD §6 finder is written by hand** — a `@Query` (JPQL) method or a `default` repository method that keeps the dictionary's name — **except** the inherited `save`, `findById` and `findAllById` and the three that Spring Data derives correctly from their names: `ProcessedSubmissionRepository.findBySubmissionId`, `ShelterRepository.findByDistrict`, and `findByDistrictIn` on a single-valued `district` (`CitizenRepository`, `DistrictOfficerRepository`, `ClientSyncStatusRepository`). The hand-written ones therefore include the names without `By` (`findAssessable`, `findClosed`, `findPending`, `findWithSpace` — Spring Data would fail at start-up), names it would misread (`findActiveByHazard(hazardId, now)` would be parsed as `findByHazard`, ignoring "Active" and `now`), `findByDistrictIn` on the collection `Organization.districts`, every finder taking a `ReportCriteria`, the geo finders (`findActiveNear`, `findNearby` — the latter implementation-only, not drawn, K-2) and the counts (`countCitizensReachedByChannel` returns a `Map`); `findByReporter(citizenId)` compares the reporter's identifier in a `@Query` (`r.reporter.userId = :citizenId`); `WarningRepository.findActiveByDistrict` and `WarningRepository.findMatching(criteria)` are `default` methods that filter by `coveredDistricts()` (the basin→district table is Java code, which JPQL cannot reach); the UC4 calculators first resolve the matching warnings with `findMatching` and then call the warning-ID finders `NotificationRepository.countCitizensReachedByChannel(warningIds, districts)`, `countCitizensReached(warningIds, districts)`, `countByWarnings(warningIds)` and `AuditRecordRepository.findEscalations(warningIds)` (PR6). Geo searches select candidates with a bounding box in the query and keep only those within the radius by a **haversine** distance computed in Java by the utility **`GeoDistance.haversineKm(a, b)`** (`shared.domain`; one implementation, no Duplicate Code — FX-02, R4G-18) — `HazardRepository.findActiveNear(location, type, district)` returns the ACTIVE hazards of the type whose districts contain `district` or whose location is within 5 km (PR5; R3G-29); `HazardReportRepository.findNearby` returns candidate reports near a report and **excludes that report itself** (R4G-35). The distance shown for each nearby report ("1.2 km") is computed by the control with `GeoDistance` — `ReportVerificationController.findNearbyReports(reportId) : List<NearbyReport>` returns the other pending or verified reports of the same type within 5 km and 24 h, excluding the selected report — and reaches the screen in `NearbyReport.distanceKm` through `showReportDetails(report, nearbyReports : List<NearbyReport>, candidateHazards : List<Hazard>)` (FX-02, R4G-02, R4E-03), not through the query. **Helper queries (R4G-26, FX-29):** a `default` finder may call public helper query methods of its own repository (e.g. a find-active-since-now query behind `findActiveByDistrict`, a bounding-box query behind a geo finder); they are implementation detail and **controls never call them** — controls call only the MD §6 names. The skeleton writes them all (§11).

## 5. SOLID checklist (L03 §3.3–3.9)

| Principle | Rule for this code | What the marker will look for (L03 §3.9 recognition guide) |
|---|---|---|
| SRP | One reason to change per class; split by responsibility, not by noun | A class whose methods do clearly different jobs (persistence + rules + formatting + messaging) |
| OCP | New hazard types, channels, metrics, export formats added by a new class or enum constant (Strategy: `NotificationGateway`, `MetricCalculator`, `ReportExporter`), not by editing an if/switch chain | `if / else if / switch` on a type string or code that chooses behaviour (a factory choosing which class to create is allowed) |
| LSP | Subtypes keep the parent's contract: no override that throws `UnsupportedOperationException`, returns `null`, strengthens preconditions or breaks `equals`/`hashCode`/`toString` | `throw new UnsupportedOperationException(...)` in an override of a **superclass** method |
| ISP | Small role interfaces; no implementer with empty or throwing stubs | `throw new UnsupportedOperationException(...)` in a method required by an **interface** |
| DIP | Services depend on interfaces (repositories, gateways, calculators, exporters, `Clock`), injected through the constructor into `private final` fields (`Objects.requireNonNull` where not Spring-managed). **(Spring)** corollary: constructor injection only — no field `@Autowired` | `new ConcreteClass()` of a collaborator inside a high-level class, stored in a field; a field typed as a concrete collaborator |

**`[0..1]` results (FE-06 as narrowed by V2C-03, MD §0.3):** a `[0..1]` operation result is `Optional<T>` in Java and `T | undefined` in TypeScript — never `null`; this is how the LSP rule "no override returns `null`" holds for `Recipient.getDeviceToken()`, `getActiveWarningForHazard`, `findActiveByHazard`, `captureLocation`, `resolveDistrict` and the rest. **Entities only:** a `[0..1]` entity field may hold `null`, but its getter returns `Optional`. **Records and embeddables are different:** a record accessor must return the component's own type, and JPA cannot map an `Optional` field, so a `[0..1]` record component (`HazardDetailsView.activeWarning`, `VerificationOutcome.activeWarning`, `ReportReceipt.report`, `ShelterOutcome.shelter`, `SyncResult.message`, …) or embeddable field (`GeoPoint.accuracyMetres`, a boxed `Double`) is a **nullable** type, documented in its Javadoc (`@return … or {@code null} if …`), and **never** `Optional`. Collections are never optional (empty instead). **`[0..1]` parameters (R3G-14, PR15):** a `[0..1]` parameter (`validateShelterDetails(details, shelterId [0..1])`, `IdGenerator.next(kind, district [0..1])`, …) is a nullable type in Java, documented in the `@param` tag ("or {@code null} for …"), **never** `Optional`, and `x?: T` in TypeScript. **`Optional` in templates (R3G-28):** Thymeleaf/SpEL does not unwrap `Optional`, so a template never reads an `Optional` getter directly: the web layer passes a view record from a mapper (`…web.mapper`, nullable component), or the model attribute is unwrapped with `.orElse(null)` in the handler.

## 6. Code smells to avoid (L03 §3.10–3.12; refactoring.guru names)

Long Method · Large Class (God Class) · Primitive Obsession · Data Clumps · Long Parameter List (>3–4 → parameter object) · Switch/If-Else Chains · Temporary Field · Divergent Change · Shotgun Surgery · Duplicate Code · Dead Code (no commented-out code, no unused members, no design-only members coded) · Feature Envy · Message Chains (Law of Demeter) · Middle Man · Inappropriate Intimacy (refactoring.guru; outside L03's list of 13 — shown only on L03's figure, R3G-27) · Alternative Classes with Different Interfaces (refactoring.guru; outside the module's 13) · magic numbers (L04 §4.4).
- **Middle Man caution:** a controller or service that only forwards adds a hop. Each layer does real work (binding/validation/mapping in the web controller, rules in the service), or the forwarding is justified by the layering (refactoring.guru keeps a middle man created to avoid dependencies) — say so in Javadoc.
- **Data Class caution:** after Introduce Parameter Object, keep behaviour with the data it uses (`Shelter.canAccommodate`, `Warning.coveredDistricts`); entities with rules keep the rules.
- **Feature Envy exception:** Strategy/Visitor deliberately keep behaviour apart from data — acceptable when documented.
- **(tooling)** PMD 7.x through maven-pmd-plugin ≥ 3.22 (3.22.0 was the first to use PMD 7 — verified in its release notes), with a written rule set in the skeleton (FE-19): `rulesets/java/quickstart.xml` plus `category/java/design.xml/GodClass`, `category/java/design.xml/CyclomaticComplexity` and the unused-code rules `category/java/bestpractices.xml/UnusedPrivateField`, `UnusedPrivateMethod`, `UnusedLocalVariable`, `UnusedFormalParameter` and `UnusedAssignment`. The whole `design` category is **not** enabled (`LawOfDemeter` and `DataClass` would flood the records and entities). PMD and Checkstyle run in every build as warnings and fail only in the final check run (§3); fix findings, never suppress without a written reason. **GodClass risk (R3G-19, PD6):** `WarningController` (ten operations plus the three-language SMS rule) and `AnalyticsController` (ten operations plus the criteria rules and scope check) are pre-empted by Extract Class (L04; for `AnalyticsController` the smell pre-empted is L03 Large Class, not Duplicate Code — FX-10, R4C-04): the rule checks live in `WarningTextValidator` and `CriteriaValidator` (MD §6, §2 rule 2), the drawn operations stay and delegate; no suppression is planned on these classes.

## 9. Refactoring practice (L04 §4.8–4.12)

- Write clean from the start: L04 §4.12 advises against refactoring under impending deadlines without regression tests.
- Process when refactoring: identify smell → tests in place → apply one technique → re-run tests → repeat (Small Steps). The code becomes cleaner, **no new functionality is added during a refactoring, and all existing tests pass afterwards** (refactoring.guru rules recorded in L04 §4.9).
- Use the catalogue names (Extract Method, Extract Class, Introduce Parameter Object, Replace Conditional with Polymorphism, Replace Magic Number with Symbolic Constant, Move Method, Hide Delegate …) in commit messages; a commit named after a refactoring technique must not change behaviour or add features.
